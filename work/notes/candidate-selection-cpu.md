# ДЗ 2: выбор кандидата на CPU

## Протокол до запуска

Зафиксирован 2026-10-12 до расчёта метрик новых правил. Изменять сетки после просмотра eval/old991 нельзя. Исходная гипотеза из [CPU-аудита](data-research-ceiling.md#6-оценка-реалистичного-потолка): oracle существенно выше голосования, поэтому проверить дешёвый выбор существующих кандидатов. Только CPU, сохранённые S1/A6.4M, без обучения, GPU и Kaggle.

### Данные и разделение

- S1 `gpu0-exp27/{heldout4k,old1024}`: greedy, первые 32 T0.7, 16 T0.5, 16 T1.0; исходный порядок сохраняется. Проверить SHA файлов и execution identity; если execution отсутствует, исполнить №26 (wall1 с, CPU2 с, четыре worker). Gold не входит в признаки или ранжирование.
- ID — сохранённый порядковый `id` исходного heldout4k. Сортировать 4096 ID по SHA256 UTF-8 строки `candidate-selection-v1:heldout4k:{id}`; первые 2048 — tune, остальные 2048 — eval. Это точные 50/50, независимо от reference. Списки ID и SHA входят в JSON.
- Old: только 991 finite reference из 1024, все eligible входят в оценку; параметры по old не выбираются. Fresh/test не читать. Heldout уже использовали в прежних исследованиях: новый split уменьшает текущую подгонку, но не заменяет финальный fresh.
- Основные пулы: greedy + первые k T0.7, k=8/16/32; отдельно все65. Контроли без greedy для k=8/16/32. Mixed при том же числе samples: k/2 T0.7 + k/4 T0.5 + k/4 T1.0 + greedy. Каждый результат сравнить с простым голосованием на **том же пуле**, mixed также с T0.7 того же k.
- Число k означает число samples, greedy добавляет один; all65 содержит 64 samples и greedy. Невычислимые кандидаты не голосуют; отсутствие numeric ответа — ошибка.

### Кластеры и признаки

- Кластеры — connected components pairwise `isclose(rel=abs=1e-6)`, как в №27. Представитель — кандидат с максимальным mean_logprob; exec-match проверяется по его значению, не по любому члену компоненты. Ties: число голосов → совпадение с greedy → средний mean_logprob → исходный порядок. Сохранить диагностику нетранзитивных компонент.
- `mean_logprob` в №27 вычислен по исходным logits без температуры sampling; `length` включает EOS. Поэтому `sum_logprob = mean_logprob × length` — сохранённая вероятность всей последовательности, без повторного teacher forcing. Для численной устойчивости использовать logsumexp.
- Дедупликация — точное равенство `code`; оставить копию с наибольшим mean_logprob, затем первую при равенстве. AST-нормализации нет. Варианты с/без дедупликации обязательны для обоих вероятностных правил.
- Цифровые числа вопроса: парсер из `research/common.py` (знак, decimal, comma-group, fraction). Литералы: AST numeric constants с учётом unary ±, уникальные значения. Покрытие c — доля уникальных цифровых значений вопроса, имеющихся среди литералов; c=0 при отсутствии чисел. Полное покрытие f=1 только при непустом наборе и c=1. Штраф u — доля уникальных литералов вне вопроса и фиксированного списка {0,1,2,3,4,7,12,24,60,100,360,365,1000}; u=0 при отсутствии литералов. Словесные/derived числа не добавляются. Это эвристика: irrelevant context и полезные производные числа могут дать неверный сигнал.
- Признаки кластера c/f/u — среднее по всем его кандидатам. Для вероятностных комбинаций используется h=c−u с фиксированным равным коэффициентом двух частей.
- Форма ответа: i=1 при абсолютном расстоянии до целого ≤1e-6; r=i+1 для ненулевого кратного10 с тем же допуском, иначе r=i. Никакой reference конкретного вопроса здесь нет. На старой stratified60k выборке №data-research посчитать finite weighted/unweighted доли целых и ненулевых кратных10; weights — finite размер шарда / finite размер его выборки.

### Выбор и отчёт

- Для каждого семейства параметры выбирать максимизацией числа exec-match **только tune**, сначала меньше активных параметров, затем меньший суммарный штраф/вес и порядок сетки. Для τ простейшее значение1; для greedy простейшее g=1; для λ простейшее1. Контроль и нулевые веса входят в сетки.
- Для pure T0.7 подбирать один набор параметров на k16/tune и без изменений применять к k8/k32. Для mixed — аналогично mixed16; all65 подбирать отдельно. Это честная чувствительность к k без трёх независимых поисков. Основной победитель — лучшее семейство по k16/tune; ties: меньше активных параметров, затем порядок таблицы. Отдельно победитель all65 и mixed16, также только tune. Eval/old не меняют победителя.
- Для каждого семейства/пула: tune count, eval и old991 exec-match; paired gains/losses, Δ в п.п. и exact two-sided McNemar против vote того же пула; 95% normal paired CI для Δ; разбивка reference BPE без EOS: <60, [60,90), [90,120), ≥120. Все поисковые результаты tune сохранить; eval для невыбранных параметров не считать. McNemar exploratory; не выдавать множество сравнений за независимые подтверждения.
- Потенциал реранкера, без обучения: oracle любого numeric кандидата; oracle представителя любого кластера; oracle только кластеров размера≥2 (также≥2 разных code как строгая диагностика); идеальное исправление только среди≥2 при сохранении остальных решений выбранного правила. Ранги правильных кластеров по выбранному score: 1/2/3/4–5/6–10/>10/нет; отдельно ошибки, cumulative top-k и доля singleton. Всё на eval/old, без подбора по этим oracle.
- Проверки: размеры/SHA/alignment, воспроизвести полный heldout vote-k16=2707 и oracle17/33/65=3314/3468/3605; проверить baseline отдельной прямой реализацией; проверить, что ранжирование не получает gold/reference length. Время CPU selection отдельно от уже выполненного execution; GPU pipeline≤180 с этим исследованием не устанавливается.

## Результаты

**Победитель только по tune/k16:** `probability-prior`, tau=0.1, delta=0.5; tune 1351/2048. Eval **1368/2048 = 66.80%**, Δ +0.29 п.п.; old991 **681/991 = 68.72%**, Δ +0.50 п.п. [Все числа, split ID, сетки и QA](../results/candidate-selection-cpu.json); [воспроизведение](../research/README.md#выбор-кандидата-на-cpu).

Зафиксированное основное правило:

$$S(C)=\log\sum_{p\in C}\exp(\bar\ell_p/0.1)+0.5\,r(a_C).$$

Здесь $C$ — кластер численных ответов; $p$ — программа; $\bar\ell_p$ — её сохранённый mean logprob; $a_C$ — ответ представителя с максимальным mean logprob; $r$ равно0 для нецелого,1 для целого, 2 для ненулевого целого кратного10. Выбирается кластер с максимальным $S(C)$; score усиливает уверенные программы и слабо предпочитает типичную форму ответа.

### Практический вывод и GPU-признаки

**Надёжного большого CPU-прироста нет.** Строгий победитель pure16/tune даёт +0.29 п.п. eval (27 gains /21 losses, p=0.471); old +0.50 п.п. (12/7, p=0.359). 95% парный CI eval [-0.37; +0.96], old [-0.36; +1.37] п.п. Рабочее ожидание для этого правила — небольшой эффект порядка0–0.5 п.п., включая возможность нулевого/отрицательного эффекта; ожидать закрытия oracle gap нельзя. Это интерпретация измерений, не прогноз leaderboard.

Однопараметрическая альтернатива `probability-mean-dedup`, τ=0.2 на pure16: eval67.09% (+0.59 п.п.;21/9,p0.0428), old69.12% (+0.91;12/3,p0.0352). Её τ выбран на tune, но семейство уступило основному победителю на2 tune-примерах. Предпочесть её **после** просмотра eval было бы новой подгонкой; оставить отдельной заранее фиксированной альтернативой для будущего fresh. Nominal p без поправки на перебор семейств не является окончательным подтверждением.

Полная вероятность последовательности ухудшает k16 на1.61 п.п.: она усиливает предпочтение коротких/уверенных программ. Умножение частоты samples на их вероятность также может повторно усилить уверенность того же генератора. Mean logprob с exact-code дедупликацией выглядит полезнее, но выигрыши малы. Pure16/tune отключил coverage/full/channel бонусы (β=0); literal penalty не переносится. Train79.16% целых подтверждает форму как слабый prior, не как средство восстановить структуру. Mixed-пулы при одинаковом k не дали устойчивого преимущества; all65 не оправдывает увеличение генерации ради такого прироста.

**Бюджет180 с:** первым замерять k8/T0.7 на исправленном быстром sampler, затем k16 только если полный pipeline укладывается. У frozen pure16-правила k8→k16 даёт +0.68 п.п. eval/+1.41 old, k16→k32 даёт +0.44 eval/−0.30 old; all65-победитель относительно pure16-победителя +1.03 eval/+0.30 old при почти четырёхкратном числе samples. По старому S1 полный test k16=309.53 с, k32=493.33 с; они превышают180 с. k8 и новый sampler этим исследованием по T4 не проверены. Голосование сохранять практическим control: у primary-победителя на k8 old хуже на0.30 п.п. Ни k32, ни all65 сейчас не рекомендовать для сдачи.

**Запас реранкера реален:** pure16/eval ideal repair≥2 даёт75.78% против66.80%, то есть +8.98 п.п.; old77.90% против68.72%, +9.18. Для≥2 разных программ остаётся +8.64/+8.88 п.п. На eval среди295 ошибок с доступным правильным кластером188 (63.7%) имеют его на ранге2–3. В all65 идеальный выбор повторяющегося кластера достигает83.40% eval/85.27% old, но не обещает достижимость этого качества обучаемой моделью.

- **Score B:** следующий GPU inference-only gate — teacher forcing существующей B по уникальным A-кандидатам на k8/k16, untempered mean logprob с EOS, затем ансамбль A/B и агрегация exact-code-dedup кластеров. Один коэффициент смешивания выбирать только на tune; B уже обучена на разрешённых исходных парах, новые таргеты не создаются. Проверить full-pool score и вариант только top2–3 кластеров для времени; экономия вычислений уменьшает oracle. Выигрыш заранее неизвестен: B greedy немного хуже A, комплементарность вероятностей ещё не измерена.
- **Обратная модель code→question / noisy channel:** score log p(question|code) проверяет согласие решения с вопросом, а не только уверенность прямого генератора. Для обучения нужна отдельная Transformer encoder–decoder с нуля и GPU; пары остаются теми же, вопрос становится target. **Серая зона допустимости:** новые строки данных отсутствуют, но направление и обучающий target меняются; условие запрещает дополнительные таргеты. Согласовать эту трактовку с преподавателем до обучения. Здесь модель не обучалась.
- **Обучаемый verifier/reranker на correctness сгенерированных программ:** оценён только oracle. Такое обучение создаёт дополнительные binary targets и по текущему условию не предлагается. Числовые coverage/novelty, размер/доля кластера, distinct-code count, длина и форма ответа уже доступны на CPU; их вычисление само по себе GPU не требует.

### Проверка и ограничения

CPU финального полного прогона: 67.1 с; цифровые признаки для обоих all65 наборов: 23.0 с. Это исследовательский проход по множеству правил и независимым проверкам, а не production timer. SHA 320 candidate-файлов и 168 execution-файлов, execution identities/alignment и 51200 независимых vote-сравнений прошли. Нетранзитивные компоненты: 3. Сохранённые исполнения переиспользованы, GPU/Kaggle/обучения нет. Fresh/test не читались; ≤180 с на T4 не проверено. McNemar exploratory без поправки на несколько семейств; old991 и heldout неоднократно использовались исторически.
