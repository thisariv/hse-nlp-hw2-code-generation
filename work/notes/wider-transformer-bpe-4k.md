# Опыт 09: ширина Transformer 128 → 256

**Получен пользовательский T4-прогон до50k; ширина ухудшила качество.** [Notebook](../notebooks/09-wider-transformer-bpe-4k-20k-pairs-50000-steps.ipynb), [новые CPU-проверки](../checks/09-wider-transformer-bpe-4k-cpu-checks.json). Продолжает [результат 08](bpe-4k-20k-pairs.md); [очередь опытов](experiment-plan.md).

## Мотивация и фактор

08 исправил форму: test AST56.7%→95.2%, ошибки отступов 754→2; весь test66.92 с. Арифметика и имена остаются слабыми, включая train-примеры. Нехватка ёмкости — гипотеза, а не установленная причина. Проверяем её перед изменением типа FFN/норм/позиций.

Меняется ширина 128→256; FFN512→1024 сохраняет отношение 4d, размер одной из 4 голов 32→64. Параметры **2 241 024→6 312 960**. Каждый токен получает больше признаков, attention/FFN могут представлять более сложные связи; конкретный прирост качества не обещаем. Общая модель остаётся encoder–decoder2+2 слоя, ReLU/Post-LN, learned positions2048, shared source/target embedding и отдельный output-head.

| Условия | 09 |
| --- | --- |
| Tokenizer | Точный собственный BPE08:4093 content IDs+3 служебных, offset3; без normalizer |
| Данные | Прежние 20k пары/19 960 вопросов, исходные программы и hashes; train64/validation64/extra192 прежние |
| Инициализация | Новые веса и AdamW, seed42; веса 08 не загружаются |
| Обучение | batch8, FP32, AdamW LR0.001/weight_decay0.01, clipping1, dropout0.1; без scheduler |
| Бюджет | 50k обновлений, 400k предъявлений/20 на пару в среднем |
| Контроли | 2k/5k/10k/20k/30k/50k, latest каждые 1000, отдельные контрольные checkpoints |
| Генерация | Прежний KV-кеш, greedy/batch32/cap512 BPE; дополнительный validation-byte512 |

Tokenizer **не обучается повторно**: сериализация 08 встроена в IPYNB как zlib/base64, только словарь/merges, без весов модели. SHA-256 `73614c921b43aa6ef715bb23bba583b96785a82304c1964f74ab11d8deef7f86` проверяется до загрузки. Никакие дополнительные файлы не требуются. Этот tokenizer обучен ранее нами только на разрешённых 20k train-парах, не является внешней pretrained-моделью. Все 40k исходных train-текстов/heldout/probes проходят exact byte-round-trip.

## Что измеряет notebook

На каждом контроле прежние train64/validation64: тот же token-weighted BPE-loss, индивидуальные greedy-программы, AST/solve/return, EOS/cap/UTF-8/exact. При **неизменном tokenizer** loss08/09 сопоставим; byte-loss по другой единице не сравниваем. Сохранённые T4-агрегаты 08 встроены и печатаются рядом с 09 на соответствующем шаге; это исторические результаты пользователя, не новые измерения.

После остановки прежнего generation timer дополнительные проверки:

- **Численная арифметика AST:** только последовательные присваивания и `return`, числа/имена/ограниченные арифметические операции. Без exec/eval, импортов, вызовов, циклов, условий и строк. Undefined/arithmetic-error/syntax-error/unsupported отдельно; unsupported не считается неправильным ответом. Совпадение с reference с допуском 1e-7 — вспомогательный показатель, не pass@1; математические ошибки эталона возможны. Число сравнимых пар у разных моделей может отличаться, знаменатели не скрываются.
- **Повторы:** хвост с периодом 1–16, ≥4 одинаковых блока и≥32 токенов; отдельно≥3 одинаковых непустых строки подряд. Максимальная длина AST-имени. Это эвристики диагностики, они не меняют выбор токенов/остановку и не доказывают функциональную ошибку.

Тот же код новых диагностик сейчас применён к сохранённым 08 train/validation/byte512-программам; компактные агрегаты встроены в 09. Старые программы/модель не перегенерированы. Совпали ранее сохранённые численные статусы 320 финальных train64+validation64+extra192 программ.

Timer train включает подготовку batch/переносы/forward/backward/clipping/AdamW/sync, исключает оценки/печать/checkpoints. Timer inference сохраняет scope08: encode/переносы/encoder/KV decode/CPU decode/AST. **Новая арифметика и повторы исключены** и имеют отдельный `extra_diagnostics_seconds_excluded`; active wall time показывает общую стоимость окна обучения. Времена 08 — одиночные замеры прошлого запуска.

Уже на 2k появятся скорость обновлений и validation64-инференса ширины 256. В конце extra192, byte512-control и **все 1919 test-вопросов** в исходном порядке. Test скачивается после обучения; нет скрытых ответов или использования test для tokenizer. Замер завершается и сохраняется даже при превышении 180 с. Теперь T4-время получено из пользовательского запуска; официальный функциональный checker ещё не применён.

## Критерий решения после результата

Ищем улучшение численных heldout-ответов и согласованности имён при приемлемых EOS/повторах и времени; AST/loss отдельно недостаточны. Сопоставлять 08/09 на одинаковых шагах/вопросах, учитывать поддержанные численным контролем подмножества и ошибки reference. При слабом результате возвращаться к отдельной гипотезе LR/оптимизации или состава разрешённых данных, прежде чем добавлять сразу несколько блоков. SwiGLU — возможный следующий самостоятельный фактор; не обязательное продолжение независимо от результата.

### Сворачивание в общий ответ

На test только31 разный текст программы. **1381/1919(72.0%)** вопросов получили один и тот же код:

```python
def solve() -> int:
    total_students = 30
    girls = total_students * 0.35
    girls = total_students - boys
    result = girls

    return result
```

`boys` не определён. AST и наличие `return` не показывают правильность решения. Уже на10k validation64 состоит из2 разных программ, обе с ошибками имён. На50k train64/validation64 дают9/8 разных программ, самый частый ответ44/51 раз. Train и validation loss хуже08 с10k; это не типичная картина «train улучшается, validation ухудшается». Причина деградации пока не установлена.

Гипотеза LR/оптимизации не считается доказанной;08 остаётся лучшей предыдущей базой. Warmup, Pre-LN и SwiGLU — последующие отдельные сравнения по результату10.
