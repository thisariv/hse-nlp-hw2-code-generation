# Опыт 07: KV-кеш при прежних весах

**Пользователь завершил опыт на T4: кеш ускорил полный test в 6.03 раза, 370.03 → 61.40 с; все 1919 ответов совпали побитно.** [Notebook с outputs](../results/07-kv-cache-byte-20k-pairs-checkpoint-50000-results.ipynb), [полный исходный results JSON](../results/07-kv-cache-byte-20k-pairs-checkpoint-50000-results.json), [сводка и опись](../results/07-kv-cache-byte-20k-pairs-checkpoint-50000-summary.json), [запуск в Colab](../notebooks/07-kv-cache-byte-20k-pairs-checkpoint-50000.ipynb), [реестр](../../JOURNAL.md).

## Гипотеза и условия

Полный decoder сейчас снова обрабатывает весь префикс на каждом шаге. Кеш должен убрать этот повторный расчёт при сохранении прежней модели и greedy-ответов. Гипотеза ускорения подтвердилась на полученном T4-прогоне. В опыте менялся способ вычисления инференса, обучение и качество остались прежними.

| Параметр | Значение |
| --- | --- |
| Веса | Checkpoint 50 000 из завершённого опыта 06; строгое совпадение SHA-256 |
| Архитектура | Encoder–decoder 2+2, ширина 128, 4 головы, FFN 512/ReLU, Post-LN, обучаемые позиции 2048 |
| Параметры / токены | 1 254 915 / UTF-8 bytes, словарь 259 |
| Инференс | FP32, greedy, batch 32, cap 512; PAD/BOS запрещены, остановка по EOS |
| Данные оценки | Прежние validation64 из JSON 06; pinned test 1919 в исходном порядке |
| Единственное изменение | Новый incremental decoder с кешем self-attention K/V и cross-attention K/V |

Оптимизатор не создаётся, train не скачивается. Закончившиеся строки остаются в batch. Другие batch, FP16, исключение finished rows и BPE — отдельные следующие факторы. Контрольный путь — точный прежний класс `SimpleTransformer`, использующий тот же объект модели/веса.

## Как работает новый путь

Для каждой новой позиции $t$ вычисляем только её hidden state. В каждом decoder-слое сохраняем self-attention $K_{\le t}, V_{\le t}$; новый $Q_t$ читает накопленную историю. Обозначения $Q$, $K$, $V$ — query, key и value, $t$ — текущая абсолютная позиция. Кеш не меняет зависимости: старые позиции causal decoder не зависят от будущих токенов.

Encoder вычисляется один раз на batch, как раньше. Его K/V-проекции для cross-attention теперь тоже вычисляются один раз на слой. Буферы self K/V заранее выделены на cap 512 и создаются заново для каждого batch; обучаемая позиция берётся по текущему $t$, не сбрасывается в ноль на каждом токене.

В SDPA `True` означает разрешённый ключ, поэтому bool-mask противоположна `key_padding_mask` старого MHA. У single-token query все поданные K/V уже из прошлого/текущей позиции: используется явная padding-mask и `is_causal=False`. `is_causal=True` для прямоугольника $1\times T$ дал бы верхнюю левую маску и скрыл историю. Dropout attention равен нулю при инференсе. Сохраняются residual/Post-LN, ReLU и финальный decoder LayerNorm.

Проекции и attention вызываются иначе, поэтому возможны небольшие ошибки округления FP32. Это не основание заранее объявлять greedy одинаковым: notebook проверяет логиты и token IDs; при расхождении validation останавливает полный test и сохраняет диагностику.

## Запуск и измерения на T4

1. Открыть notebook в Colab с **T4**. Загрузить исходный `hw02-byte-20k-continue-10000-to-50000.zip`; другой архив/веса проверку hashes не пройдут.
2. Проверить логиты на 3 вопросах с разными длинами, padding и позициями до 297 включительно; tolerances `atol=rtol=1e-4`. Проверить неизменность весов.
3. Прогреть оба пути; на прежних validation64 выполнить 3 повторения, чередуя порядок. Сравнить token IDs, стабильность повторов, median seconds, throughput и peak GPU-memory. Измерения 06 записываются отдельно как сохранённая история.
4. При полном совпадении validation сгенерировать **все 1919 test-ответов обоими путями**, без остановки на 180 с. Сравнить все последовательности, полное время и cached-бюджет 180 с. Различия test сохранить для анализа.
5. Скачать ZIP и отдельно IPYNB с outputs. ZIP содержит результаты, обе test-генерации при завершённом test и manifest с размерами/hashes; весов в нём нет. Последняя ячейка работает и после остановленной проверки, исключая старые test-файлы из частичного архива.

Таймер включает кодирование вопросов, переносы, encoder/подготовку кеша, greedy, CPU token conversion/decode и AST/return/exact. Прогрев, проверки префикса, сравнение двух путей, печать, скачивание и запись файлов исключены. Разбор AST не исполняет программы. Официальные checker и границы его таймера ещё требуют уточнения; test-файл этого опыта — диагностика, не посылка боту. Pass@1 не измеряется.

## CPU-проверки при подготовке

До пользовательского запуска агент использовал **реальные веса 50 000, FP32, PyTorch 2.14.1 / CPU**: [проверки подготовки](../checks/07-kv-cache-cpu-checks.json). Это сохранённые предварительные проверки; при текущем разборе они не повторялись.

- Последние logits на 3 padded-префиксах совпали в допуске: 9 позиций 0–297, максимальная абсолютная ошибка $1.3352\cdot10^{-5}$. Дополнительно проверены позиции 255 и 511 с законченной/PAD строкой.
- На validation[0], [1], [16] ordinary/cached greedy до cap 512 совпали побитно. Длины 145, 154, 512; у первых двух EOS, у последнего cap без EOS. Повтор с новым кешем дал те же IDs.
- По вызовам подтверждены encoder один раз, cross K/V один раз на слой, self QKV и cross Q только для одной новой позиции. Проверены предел буфера и форма входного токена.
- С контролируемой head проверены EOS на первом/последнем шаге, разные моменты завершения строк и запрет PAD/BOS. После fixture восстановлена исходная head; fingerprint весов и исходные файлы не изменились.
- Все ячейки синтаксически проверены. В CPU smoke исходных управляющих ячеек **сокращены только тестовые бюджеты**: cap 8, batch 2, validation 3, test 4, 2 повтора. Проверены gates, остановка при mismatch, CRC/manifest ZIP и частичная выгрузка без устаревших test-генераций. Это проверка кода, а не полный test или новая оценка качества.

Validation64 совпали во всех трёх контрольных сравнениях; сохранённые 64 программы совпали с опытом 06. На test совпали **все 1919 token sequences и тексты**. Fingerprint весов до/после совпал с исходной подготовкой. Мы ускорили прежние ответы, а не обучили более качественную модель.

### Качество прежней модели

| Статическая метрика | Validation64 | Test1919 |
| --- | ---: | ---: |
| EOS | 61 / 64 — 95.3% | 1820 / 1919 — 94.8% |
| Cap 512 без EOS | 3 / 64 — 4.7% | 99 / 1919 — 5.2% |
| AST-валидная программа / `solve` | 41 / 64 — 64.1% | 1088 / 1919 — 56.7% |
| `return` со значением внутри `solve` | 40 / 64 — 62.5% | 1060 / 1919 — 55.2% |

На test 831 AST-невалидная программа; **754 ошибки (90.7% невалидных)** относятся к отступам: 574 `unexpected indent`, 180 `unindent does not match...`. На validation 20 из 23 AST-ошибок — отступы. Это новый статический разбор всех сохранённых программ, не исполнение и не pass@1. Ошибки чисел/операций/имён из validation06 сохраняются, поскольку программы те же. Python-синтаксис и наличие return не доказывают правильный числовой ответ.

Последний validation teacher-forcing loss **0.7666764** — из опыта 06, в 07 loss не измерялся. Последний темп обучения **42.10 обновления/с**, 40 000 добавочных шагов за 950.02 с — также история 06. Кеш работает только при авторегрессионном инференсе; ускорение training forward/backward этим опытом не проверялось.

### Память и оставшиеся вычисления

На validation пик уменьшился в **2.85×**, но на полном test пик **не изменился**. Это счётчик памяти tensors PyTorch с reset перед каждым путём, а не отдельно память decoder и не показание `nvidia-smi`. Код раздельно измеряет каждый путь; printed outputs и JSON согласованы.

Наша гипотеза: общий encoder на длинных padded test-вопросах определяет глобальный пик обоих путей. Максимальный padded source — 717 байтовых токенов; encoder и его padding одинаковы. Это объяснение согласуется с кодом/данными, но требует per-stage профиля; причину пика не измеряли. Не переносить снижение памяти validation на весь test.

В test 60 batch, 49 доходят до cap 512. Полезно выдано 391 751 токен из 933 024 слотов; **58.0% слотов** относятся к уже закончившимся строкам. Finished rows остаются, поэтому запас дальнейшего ускорения есть. Сейчас временной лимит уже пройден в измеренном scope; это позволяет вернуть основной приоритет качеству.

## Вывод и следующий шаг

Гипотеза 07 подтверждена: убрать полный пересчёт prefix удалось без изменения ответов на проверенных наборах. Сохранить кеш для следующих вариантов и повторять полный test после смены токенизации/архитектуры. Один test-замер не характеризует разброс времени между сессиями T4.

Следующий обучающий фактор — **собственный обратимый BPE** на прежнем разрешённом train, прежние 20 000 пар и блоки 2+2/128. Сначала round-trip отступов/новых строк/чисел и длины; затем новая модель с нуля. Гипотеза: более цельные фрагменты кода и меньше шагов помогут, в том числе форме программы; улучшение отступов/арифметики заранее не гарантировано. Словарь меняет embedding/head и число параметров, поэтому фиксировать их. Не сравнивать напрямую token loss разных токенизаций.

Функциональная оценка остаётся открытой: нужен checker/формат и проверка вычисляемых ответов. Сравнение с исполнением исходных validation-программ может быть только proxy — в исходных таргетах есть ошибки. Пока AST/return/EOS не заменяют pass@1. FP16, batch и исключение finished rows можно проверять позже отдельно; усложнение архитектуры сейчас не требуется для проверки гипотезы токенизации.
