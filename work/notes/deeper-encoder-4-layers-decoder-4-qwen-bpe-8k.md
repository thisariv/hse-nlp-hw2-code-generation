## Гипотеза и контроль

Пользователь выбрал увеличить энкодер и отложить LR/batch. Проверяем, помогут ли дополнительные преобразования вопроса выделять числа, объекты и отношения перед cross-attention декодера. Равное число encoder/decoder слоёв не является требованием; encoder bottleneck пока не доказан.

Непосредственный контроль — [20: encoder2/decoder4](deeper-decoder-4-layers-qwen-bpe-8k.md). На100k: CE1024 0.748972, byte NLL0.219251, reference170/888, ручной13/74, чистый train56.75мин и test1919 51.74с. Эти числа — сохранённые T4-результаты пользователя, не новый запуск. №19/18 остаются дополнительными контролями; ручной12/14 из74.

Один encoder-слой содержит788048 параметров. Прибавка двух слоёв:

$$P_{21}=P_{20}+2P_{enc}=10\,510\,816+2\cdot788\,048=12\,086\,912.$$

$P_{21}$ и $P_{20}$ — число обучаемых параметров моделей; $P_{enc}$ — число параметров одного encoder-слоя. Дополнительные self-attention+SwiGLU FFN сохраняют размер выхода энкодера и интерфейс cross-attention. Число параметров подтверждено созданием полной модели наCPU.

Меняется расход RNG при инициализации: одинаковый seed не даёт одинаковых начальных общих весов с20. Это один запуск, не доказательство оптимальной глубины.100k×batch8 дают800k предъявлений; sampling/coverage tracking прежние.

## Оценка

- На50k/75k/100k: старые heldout1024/фиксированные reference888, прежние256/223, CE и NLL на исходный UTF8-байт, парные приобретения/потери, EOS/имена/AST, индивидуальные программы. История20/19/18 встроена, их модели здесь не запускаются. CE сравним с20/19 по одинаковому tokenizer, с18 используем byte NLL.
- Добавлена автоматическая оценка **тех же74 вручную решённых численных задач** из аудита100;26 исключённых остаются исключёнными. Принимаются прежние варианты ответа для473 и557; неизвестные unsupported учитываются отдельно. Все девять сохранённых score18/19/20 на50k/75k/100k воспроизведены новой функцией. Правила зафиксированы до запуска21.
- Ручные ответы используются **только после генерации на heldout**. Они не добавляются в train, BPE-train, loss или обучающие таргеты. Это диагностика на старом наборе, который уже влиял на выбор опытов; не официальный pass@1.
- Свежие1024 сохраняются в ZIP, **не оцениваются**. Отдельный byte512-контроль64 и полныйtest1919/batch32/cap512/KV-cache остаются прежними.

Критерий полезности — улучшение решений задач и loss при приемлемой скорости; reference proxy сам по себе недостаточен из-за ошибок эталонов. Если loss снизится, а ручные решения не улучшатся, не объявлять устранение проблемы чисел.

Энкодер вычисляется один раз на входной батч, декодер — для каждого генерируемого токена. Увеличение энкодера имеет другой профиль стоимости, чем decoder depth; На этапе подготовки скорость21 была неизвестна; полученный T4-замер приведён ниже. Заново измерять чистое обучение/active wall/test. Тестовый таймер включает encoding/transfers/encoder/KV-decode/CPU decoding/AST; исключает загрузку/setup/loss/дополнительный numeric audit, как в20. Проверяется180с в этой области таймера; официальный scope ещё не уточнён.

### Проверка смысла и ограничение старого оценщика

Исходный evaluator не поддерживал augmented assignment. В21 задача0 правильно решена как `crayons=10; crayons-=2; crayons-=4`, но получила unsupported. При новом разборе добавлена **только в локальный аудит** безопасная AST-замена `x op= y` на `x=x op y` для простых имён. Произвольный Python не исполняется; calls/imports/subscripts/loops по-прежнему запрещены. Одинаково пересчитаны18/19/20/21 на тех же74 ответах.

Исходный счёт13→18 в notebook/JSON сохраняется. Дополнительный аудит14→19 снимает ограничения `+=/-=`, не меняет train/таргеты/manual labels/reference888. В21 задача821 с `students += 8` вместо вычитания даёт49 вместо33 и признана неправильной; unsupported не трактуется автоматически как ошибка.

Примеры прироста21:5 монет ×4→20 (20 выдавал25);2×10−5 книг→15 (было20);сад36 в4раза меньше другого→144 (было9);$20 вмесяц за12 месяцев→240 (было100). Есть потери:3 дюжины→3/12 вместо36;нехватка денег250−150→0;маршрут15+(15+20)+2(15+20)→210 вместо120. Выбор чисел, направление операций и повторное использование переменных остаются основными ошибками. Cross-attention получает полезный источник, но это не гарантирует понимания отношений.

## Проверка LR после21: выполненный опыт22

21/100k — текущий кандидат по смысловому качеству; №20 сохраняется как более быстрый контроль с меньшим CE. Пользователь предложил проверить LR из-за замедления на 80–100k. Сначала проверяем оптимизацию уже обученной модели 4+4.

Есть сохранённый **checkpoint 21/75k**. Предлагается восстановить веса, AdamW, Python/Torch/CUDA RNG и покрытие данных, затем **повторить те же 25k updates до 100k**, меняя только LR: cosine 0.0001→0.00001 вместо постоянного 0.0001. Сохраняются данные, tokenizer, batch и архитектура; без нового warmup и сброса оптимизатора.

Контроль уже выполнен: исходный 21/75k→100k при постоянном LR 0.0001. Нужен один новый запуск на 25k. Одинаковые начальные веса, AdamW, RNG, порядок батчей и итоговые 100k позволят проверить влияние LR при равном бюджете. По текущему темпу 25k занимают около 17 минут чистого обучения; время нового T4-запуска нужно измерить.

Сравнить финальные 100k по heldout1024, reference888, тем же 74 ручным ответам с поддержкой AugAssign, парным изменениям, EOS, именам и test1919. Во время опыта сохранять loss16 для преемственности и оценки loss на более крупном наборе. Снижение LR может улучшить донастройку или замедлить обучение; результат заранее неизвестен.

Размер batch остаётся отдельным фактором; fresh1024 — для финального сравнения выбранных моделей. Формат официального бота требует уточнения. Пользователь выбрал этот план; подготовлен [22: cosine на последних 25k](cosine-tail-from-75k-to-100k.md). Его T4-результат получен: CE.7785 против21.7758,reference173 против178/888,manualAugAssign19/74 тотже,формат/test лучше (57.60с). [Разбор22](cosine-tail-from-75k-to-100k.md) содержит результат/новые проверки; описанный выше протокол был выбран до его получения.
